# MusicMe — Samsung DEV end-to-end plan (Render control plane + portable GPU)

Revised 21 October 2026. Everything in this plan is prepared locally only. No Render or GPU resource has been
created, changed or deployed, no account was connected, and no charge was incurred.

The target remains **DEV-only song generation**. Production generation stays disabled. Production authentication,
Room migrations, the BeatIQ Library, user data, backups and signing are outside this work and are unchanged.

## 1. Recommended architecture

```text
Samsung BeatIQ debug APK (isolated dev-* identity; no reusable credential)
        │ HTTPS bearer JWT
        ▼
Render project: beatiq-musicme / environment: samsung-dev
  network isolation ON, environment protection ON, previews OFF, auto-deploy OFF
  ├─ beatiq-musicme-dev-auth       0.5 CPU / 512 MB + 1 GB private disk
  │    DEV sign-in/refresh; authenticated revocation endpoint; separate generated secrets
  ├─ beatiq-musicme-audio-dev      0.5 CPU / 512 MB, ephemeral validation scratch only
  │    authenticated API, durable job coordinator, quotas, PostgreSQL cost ledger, WAV validation,
  │    signed short-lived downloads and one bounded background job thread
  └─ beatiq-musicme-audio-dev-db   private PostgreSQL, 0.1 CPU / 256 MB + 1 GB
        │ private S3 API
        ├─ dedicated private DEV R2/S3 bucket (completed songs; direct presigned GET)
        │ HTTPS; Modal proxy credentials + independent worker bearer token, Render secret only
        ▼
External GPU (first choice: Modal T4, min=0, max=1, 120 s idle scale-down)
  musicme.gpu-job.v1 worker → exact pinned ACE-Step runner → verified WAV → immediate delete
```

The optional songwriting service is a separately costed Blueprint and database in an independently isolated Render
project. It is not needed when the Samsung test starts from reviewed/manual lyrics, so omit it from the cheapest
first test. The prepared files are:

- `infra/render/musicme-dev.yaml`: DEV auth, audio API/job coordination, audio PostgreSQL and private object storage.
- `infra/render/musicme-production-disabled.yaml`: separate future production boundary with generation off.
- `infra/render/musicme-songwriter-addon.yaml`: optional songwriter API plus its own PostgreSQL.
- `services/musicme-audio/deploy/worker/Dockerfile`: provider-neutral NVIDIA container.
- `services/musicme-audio/deploy/modal/musicme_worker.py`: Modal T4 adapter.

### Why Render is the control plane, not the GPU plane

Render is economical for small continuously available Python services and managed PostgreSQL, but it does not offer
the scale-to-zero pay-as-you-go NVIDIA worker required here. The GPU URL and credential document are the only
provider-specific control-plane settings. Moving among Modal, RunPod and Vast.ai does not change Android, the audio
API, the job schema or ACE-Step.

The DEV audio API owns one bounded background thread, avoiding another always-on Render instance. Jobs/costs are in
PostgreSQL and songs in object storage, so future public scaling can set `MUSICME_AUDIO_RUN_WORKERS=false` on web
instances and run `audioservice.worker_service` as one or more separately scaled coordinators. Keep one combined API
instance for Samsung DEV.

## 2. Isolation and security model

- Render resource names all start `beatiq-musicme`; they live in new protected environments with private-network
  isolation enabled. The databases block public ingress. Do not adopt, rename, attach or share any BioAegix or other
  existing service, database, disk, environment group or secret.
- The DEV auth JWT secret and internal revocation token are generated by Render. The audio/songwriter services read
  the dedicated auth service values; neither value reaches the APK.
- Public hosted MusicMe refuses to start unless HTTPS public URLs, issuer, audience and authenticated HTTPS
  revocation are configured. Revocation responses are no-redirect, JSON-only, bounded to 64 KiB, cached for five
  seconds and fail closed.
- GPU calls have two gates on Modal: Modal proxy auth and the worker's own constant-time bearer check. The Render
  secret is JSON containing the worker token and `Modal-Key` / `Modal-Secret` headers. RunPod/Vast use the same field
  without Modal headers. Every new provider receives a new token.
- Worker requests are schema-checked and limited to 64 KiB. Job ids are unguessable and owned by the worker token;
  exact repeat submissions are idempotent and a changed body under the same id is rejected. There is one active
  render and at most one queued render.
- Output lives in a mode-0700 temporary directory and mode-0600 files. It is hash-checked in transit, parsed and
  validated as 16-bit PCM WAV (sample rate, channels, duration, silence, clipping and maximum size), copied to private
  private object storage, then deleted from the GPU. Worker output and job records also expire on TTL and are wiped
  on shutdown. The private object is size/hash verified after upload before its database row is published.
- Cancellation reaches the GPU; service shutdown cancels the active remote job. A worker deadline and provider
  container timeout remain backstops. One lost serverless worker may be resubmitted once with the same id; repeated
  loss fails cleanly.
- Lyrics, tokens and credentials are not logged. Tests exercise this boundary. Test only with synthetic/non-personal
  lyrics until provider privacy review is complete.

## 3. Validated generation behaviour preserved

The GPU worker invokes the same `AceStepEngine` runner boundary and does not reimplement model inference. These pins
remain in `audioservice/acestep/manifest.json` and are verified before load and again in the hello handshake:

- ACE-Step 1.5 repository tag `v0.1.8`, commit
  `dce621408bee8c31b4fcf4811682eb9359e1bc94`.
- `ACE-Step/Ace-Step1.5` weights revision
  `19671f406d603126926c1b7e2adc169acbcade22` and the existing eight exact SHA-256 file hashes.
- Python 3.12; `torch==2.10.0+cu128`; `acestep-v15-turbo`; text-to-music only; no LM planner, reference audio,
  cover/repaint, timbre cloning or LoRA.
- The existing parameter mapping, eight inference steps, offline/download blocking, runner environment allow-list,
  and float16 lyric-encoder numerical correction plus GPU self-test are unchanged.

This repository's fake-provider and fake-runner tests do **not** constitute a new real-GPU validation. The earlier
GPU validation is the basis for preserving these exact choices; the packaged container still needs its own smoke
test on the approved provider.

## 4. Provider comparison for the first Samsung DEV test

Current list-price facts below were checked against official provider material on 21 October 2026. Marketplace
availability, tax, bandwidth and an account's credits/spend controls must be checked in the owner's dashboard at the
approval gate.

### Modal T4 — recommended first test

- T4 GPU: `$0.000164/s` (`$0.5904/h`). With the configured 2 CPU cores and 16 GiB RAM, current list rates bring the
  running-container estimate to about **$0.813/h** before tax.
- Billed per second while a container is running, including idle warm time. This adapter has zero minimum warm
  containers, one maximum container, 120-second idle scale-down and a 15-minute container timeout.
- The `oxjadekanye` workspace was confirmed on 23 October 2026 with **$2 usage and spend limits**. Keep both limits
  unchanged; do not substitute a public plan headline for the workspace-specific dashboard controls and do not
  activate or change billing without approval.
- The 6.34 GB pinned weights live in a Modal volume. The list rate is `$0.09/GiB/month` (about `$0.57/month`), while
  current Starter pricing says up to 1 TiB of volumes is included. Applicability to this specific workspace remains a
  dashboard check. Cold image/model start time is **unverified**. Modal proxy auth prevents unauthorised requests
  from waking the GPU.
- Estimated one-song compute: roughly `$0.03–$0.15` for 2–10 billed minutes. At `$0.8126/h`, the configured
  900-second container timeout plus 120-second idle tail bounds one container attempt at about `$0.23` before any
  regional multiplier. The existing **$2 usage and spend limits** are the provider backstop for carefully observed
  tests; do not raise them. Configure the Render-side DEV ledger to `$0.75/day` for headroom and delete the volume afterward
  if it is not needed.

### RunPod

- Serverless flex workers scale to zero and bill from worker start to stop. Current official 24 GB class list rate is
  about **$0.69/h**; exact GPU assignment/cold-start behaviour for this image is **unverified**.
- On-demand Pods list approximately A5000 `$0.27/h`, RTX 3090 `$0.50/h`, L4 `$0.59/h`, but Pods add storage and need
  explicit stop/termination. The generic HTTP image fits Pods/proxy directly; RunPod's standard serverless handler
  API would need a thin adapter not included in the first-test path.
- Potentially cheaper raw compute than Modal, but shutdown discipline and adapter work make it second choice. Set an
  account spend limit and verify that container exit actually stops billing before use.

### Vast.ai

- Marketplace compute is per second with no stated minimum, and can be the lowest raw price. The exact suitable T4,
  L4, A5000 or 3090 listing at test time is **unverified** and host quality varies.
- Storage and bandwidth are host-priced; a stopped instance can continue charging for storage. Destroy it after
  retrieving diagnostics/output. The worker's 15-minute idle exit helps but is not a substitute for destruction.
- Highest operational/security variance: inspect host reliability, driver (CUDA 12.8 wheels require a compatible
  driver), network exposure and total price. Use an SSH tunnel and loopback worker binding where practical.

### Decision

Run the first end-to-end test on **Modal T4** because it matches the validated T4 float16 path, has the cleanest
serverless scale-to-zero and has two authentication layers. RunPod serverless may have a lower advertised 24 GB rate,
but the missing handler adapter and uncertain assigned hardware outweigh pennies on one smoke test. Re-evaluate
RunPod after the protocol test; use Vast only when its live all-in price and host meet the security checklist.

## 5. Render capacity and monthly cost

An active Render workspace subscription pays for workspace features; it does **not** include arbitrary web-service,
PostgreSQL or persistent-disk compute. Without inspecting the owner's Render dashboard, existing unused resources and
credits cannot be established. The safe planning assumption is that every new isolated resource is incremental.
Reusing an existing BioAegix/app database, service, disk or credential is prohibited even if it appears idle.

Estimated incremental list price for the recommended hosted control plane:

- DEV auth web service, 0.5 CPU / 512 MB: `$7.00/month`; 1 GB disk: `$0.25/month`.
- Audio API/job coordinator, 0.5 CPU / 512 MB: `$7.00/month`; no persistent song disk.
- Audio PostgreSQL, 0.1 CPU / 256 MB with its included 1 GB storage: `$6.00/month`.
- **Base Render total: about `$20.25/month`**, plus bandwidth over any workspace allowance, tax and GPU usage.
- Optional songwriter web service plus separate smallest PostgreSQL: about **`$13.00/month`** more, for a total near
  **`$33.25/month`**. Its external model endpoint can add separate compute/API cost.
- Private R2 Standard storage currently has a 10 GB-month/operation free allowance and then lists `$0.015/GB-month`;
  account eligibility and actual usage are **unverified**, so budget it separately rather than assuming zero.

These are estimates, not quotes. Verify the preview page before an approved Blueprint sync. The previous Mac-hosted
option is superseded: the permanent Samsung DEV control plane is Render plus a private object bucket.

Compared with alternatives:

- Render + R2 + Modal: selected managed control plane and GPU scale-to-zero; about `$20.25/month + storage/GPU usage`.
- A continuously running RunPod/Vast all-in VM: avoids Render services but couples secrets/data/API availability to a
  GPU host and risks idle charges; not recommended.
- A fully serverless custom cloud stack could reduce idle control-plane cost, but introduces provider-specific queues,
  functions, object storage and auth work that is disproportionate to this DEV gate.

## 6. Render environment configuration

The Blueprints contain no literal secret. Important generated/referenced values are:

- Auth: `MUSICME_DEV_AUTH_HOME`, `MUSICME_DEV_AUTH_ALLOW_PUBLIC=true`, generated
  `MUSICME_DEV_AUTH_JWT_SECRET`, generated `MUSICME_DEV_AUTH_INTERNAL_TOKEN`.
- Audio identity: referenced `MUSICME_AUDIO_JWT_SECRET`; issuer `beatiq-dev-auth`; audience `musicme-dev`;
  `MUSICME_AUDIO_JWT_REVOCATION_URL=https://<auth>/internal/revocation`; referenced revocation token.
- Audio data: private `MUSICME_AUDIO_DATABASE_URL`; `MUSICME_AUDIO_GPU_LEDGER_BACKEND=database`; ephemeral
  `MUSICME_AUDIO_STORAGE_ROOT`; private S3 endpoint/bucket/access credentials and `dev` prefix; generated,
  independent `MUSICME_AUDIO_SIGNING_SECRET`.
- GPU: `MUSICME_AUDIO_ENGINE=remote_gpu`, `MUSICME_AUDIO_WORKER_URL`, secret
  `MUSICME_AUDIO_WORKER_CREDENTIALS_JSON`, allowed host suffixes, one worker, timeout and daily spend/render limits.
- Public gate: `MUSICME_AUDIO_ALLOW_PUBLIC_DEV_SERVICE=true`, exact HTTPS
  `MUSICME_AUDIO_PUBLIC_BASE_URL`, host `0.0.0.0`, issuer/audience and hosted revocation.
- Songwriter add-on: its own database and model endpoint/name/version/API key; it references only the dedicated DEV
  auth values.

`sync: false` values must be entered in Render's secret UI. The worker token and Modal proxy credentials also live in
Modal secrets; the same values are never put in `local.properties`, source control or the APK.

## 8. Approval gates and exact real-song steps

### Gate A — approve hosting and budget

Owner explicitly approves the estimated `$20.25/month` Render base resources, a private DEV object bucket/token and
Modal account setup/payment method, `$2` test cap, weight volume creation and endpoint deployment. Until then, stop:
local preparation is complete.

### Gate B — create provider secrets and deploy one scale-to-zero worker

1. Create a random 32+ character worker token in a secret manager; do not paste it into chat or Git.
2. Create isolated Modal environment `musicme-dev`, then create Modal secret `musicme-gpu-worker-token` there,
   containing `MUSICME_WORKER_TOKEN`.
3. Run the prepared CPU-only `prepare_weights` function with `--env musicme-dev`. It downloads only the pinned folders/revision and verifies
   every committed SHA-256. This may incur storage/CPU charges and therefore needs approval.
4. Deploy `services/musicme-audio/deploy/modal/musicme_worker.py` with `--env musicme-dev`. Record its HTTPS URL. Create a dedicated Modal proxy token
   scoped for this endpoint and verify an unauthenticated hello is rejected without starting GPU work.
5. Verify dashboard limits: T4, min 0, max 1, idle 120 s, function timeout 900 s and owner-defined spend alert/cap.

### Gate C — start the isolated Render control plane

1. Create the separately approved private DEV bucket and bucket-scoped object credentials; keep public access off.
2. Review unique resource names and pricing, import `infra/render/musicme-dev.yaml`, enter every prompted value and
   approve the Blueprint preview. Confirm `/readyz`, private database ingress, network isolation and protection.
3. Create the DEV user with a one-off approved shell action. Do not import the songwriter add-on unless its extra
   monthly/model cost is accepted. Do not import the production-disabled Blueprint for Samsung DEV.

### Gate D — build/install on Samsung DEV

1. Put only public Render DEV base URLs in untracked `local.properties`. No JWT, worker, object-store or provider
   credential goes in this file.
2. Build the debug APK. After explicit install approval, connect the Samsung with USB debugging, apply port reversal
   if local, and install the debug APK. Never install this flow as a production/release build.
3. Sign in as the isolated `dev-…` user. Create a 30-second English test song from synthetic lyrics, observe progress,
   cancel one attempt, then complete one attempt. Confirm the result reports real audio, plays, keeps, survives restart,
   downloads and deletes. Confirm another DEV identity cannot access it.
4. Revoke the user and confirm the next API call fails closed. Inspect service logs for absence of lyrics/tokens.
5. Confirm the Modal dashboard returns to **zero containers** after the 120-second idle window. Record billed seconds,
   cold-start time, render time, WAV metadata and spend. This is the first point at which the new container and Samsung
   path may be described as genuinely validated.
6. Delete/disable the test endpoint and volume if no further testing is planned. On RunPod stop/terminate; on Vast
   destroy the instance so storage cannot continue billing. Render teardown is a separate destructive approval.

## 9. Remaining risks

- Modal build, weight-volume preparation, cold start and this packaged image are not yet run on a real GPU.
- Current Render capacity/credits are unknown until the owner reviews the dashboard; subscription does not make new
  compute free.
- S3-compatible storage has not yet been exercised against a real private bucket; credentials, direct presigning and
  lifecycle rules require provider validation.
- Provider spend limits differ. The PostgreSQL ledger is conservative and fails closed, but the provider dashboard
  remains the authoritative billing control.
- Serverless restart loses worker-local job state. The client recovers once; repeated eviction fails rather than
  double-spending indefinitely.
- Cancellation is cooperative until ACE-Step's runner process is killed. Provider billing can include cold start and
  the configured warm tail even after a user cancels.
- ACE-Step quality, lyric intelligibility, originality and legal/product approval remain separate open gates.
- Render public services and model providers process synthetic test lyrics; complete privacy/legal review before real
  user content or any production enablement.
